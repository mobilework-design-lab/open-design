# 需求发现与视觉确认

## 完整性矩阵

只追问会改变设计或交付的缺口。

| 维度 | 足够继续的证据 | 缺失时询问 |
|---|---|---|
| 产品 | 是什么、核心价值或任务 | 产品/服务及其关键价值 |
| 受众 | 主要使用者及使用语境 | 谁使用、熟练度、场景 |
| 目标 | 页面唯一首要动作或判断 | 用户看完要做什么 |
| 范围 | 页面、区块和信息优先级 | 必须出现与可省略内容 |
| 内容/资源 | 文案、数据、品牌、本地素材是否已有 | 哪些可用，哪些可明确标注为示例 |
| 响应式 | 主要设备及窄屏约束 | 移动优先、桌面优先或同等 |
| 交互 | 控件、验证、数据状态 | 必须可操作和演示的状态 |
| 输出 | 单 HTML 或多文件 | 无法从页数与编辑诉求推断时询问 |

## 第一轮：一次集中提问

用原生 `question` 把所有关键缺口放在一次短交互中，优先给 2–3 个互斥、易选的答案并允许自定义。不要把问题拆成连续的逐字段审问，也不要询问不会改变产物的偏好。答案写入 `collecting` brief。

## 第二轮：2–3 个视觉方向

每个方向必须说明六点：信息层级、字体性格、色彩角色、密度与留白、图像或图形策略、动效克制。名称要能描述产品气质，例如“高密度控制台 + 窄幅数字排版”，不能只写“现代”“简约”。方向之间至少在层级、密度或字体/色彩策略上有两个实质差异。

用 `question` 要求用户选择、混合或调整。选择前状态为 `style-proposed`；选择后把最终方向的理由和禁用项写入 `visualDirection`，状态改为 `confirmed`。

## 路径判断

- 不完整：第一轮问题 → 方向提案 → 阻塞确认。
- 信息完整但视觉未确认：跳过第一轮 → 方向提案 → 阻塞确认。
- 用户已给完整且明确的视觉方向：简短复述后确认；若用户原话已构成确认，可直接落盘。
- 明确要求立即生成：不再提问，把推断写入 `content.assumptions` 或相应字段，并标记 direct authorization。

## 失效规则

产品定位、主要受众、核心目标、页面范围或输出模式改变：`confirmed -> collecting`，重新补齐并确认。只改变视觉方向或信息结构：`generated -> confirmed`，无需重问已稳定的产品事实。文案微调、颜色数值或局部间距不使整个 brief 失效。

允许持久状态仅为 `collecting`、`style-proposed`、`confirmed`、`generated`、`finalized`、`delivered`。不要创造近义状态。
